## 变更概要

## 六视角扫描结果

### 1. 攻击者视角

导入器不是 HTTP 接口，只有能进入容器执行命令的运维主体可调用。SQL 均使用 GORM 参数绑定，没有字符串拼接注入。图片文件名在 `backend/cmd/import-restaurant-botanic/main.go:193` 验证为 basename，阻止 `../` 路径穿越。目标产品在 `backend/cmd/import-restaurant-botanic/main.go:369` 按精确 ID 查询，并在 `backend/cmd/import-restaurant-botanic/main.go:376` 校验供应商与英文名称，防止误写同 ID 的其他实体。未发现阻断问题。

### 2. 泄露者视角

输出仅含 category、region、supplier 和 product ID/名称，不输出 DSN、密码或 token。错误信息可能包含目标 ID、供应商 ID 和名称，但仅写入容器命令行日志，均不属于凭证或个人敏感信息。metadata 记录来源 URL 和 REQ ID，不含密钥。未发现阻断问题。

### 3. 并发者视角

产品及其关联替换在 `backend/cmd/import-restaurant-botanic/main.go:145` 的单一数据库事务中执行，失败可整体回滚。并发运行两个 importer 仍可能在删除关联后并发插入而形成重复关联，因为没有产品行锁或唯一约束；当前工具只由单次 demo 部署命令调用，实际并发概率低，评定为 Low。建议未来在真实 PostgreSQL 集成测试中加入 `FOR UPDATE` 或用部署锁串行化执行。

### 4. 边界者视角

审查中发现原实现只按名称定位，目标缺失时可能创建新 ID，不符合精确 product_id 范围。现已在 `backend/cmd/import-restaurant-botanic/main_test.go:17` 锁定 ID+名称白名单，并在 `main.go:370` 对缺失目标直接报错；身份不匹配也会在写前失败。图片缺失、非法文件名、目录不可写和数据库失败均显式返回错误。图片单测目前只验证存在性，没有解码 JPEG/校验尺寸，评定 Low，不阻塞。

### 5. 依赖者视角

数据库连接、文件系统和 demo SSH 任一失败均停止流程，没有静默成功。SSH 在部署期间有间歇性拒绝，部署脚本能在前置检查失败时安全退出；一次 Nginx 重复同步失败发生在新 backend 已 healthy 后，公网 health 验证为 200。没有外部官网图片运行时依赖，封面随镜像携带并复制到持久化 upload 卷。未发现阻断问题。

### 6. Scope 审计者视角（Karpathy）

审查发现原实现通过整行 `Save` 更新已有产品，可能将评分、精选、排序、OCTO 和人工翻译锁等非需求字段归零，属于 High 数据一致性风险；同时 metadata 仍引用旧 REQ。现已改为 `backend/cmd/import-restaurant-botanic/main.go:419` 的显式字段白名单，并由 `main_test.go:47` 防止运营字段进入更新 map；REQ provenance 改为 `REQ-20260811-0049`。旧 legacy 迁移会删除重复产品，超出“只补全五个既有草稿”范围，现已移除。其余变更均可追溯到 PRD 的 importer、cover、Docker 包装或测试要求。
